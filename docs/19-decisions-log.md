**D-040 — RepEngine v1 details fixed by the reference implementation** — Accepted — 2026-10-20

every vector (quality ±1). Details that doc 05 left open: (1) depth = (shoulder y − shoulder y at the last TOP) /
median upper-arm length of the last 30 TOP frames (image pixels); (2) evaluation order = BODY_NOT_VISIBLE →
KNEES_DOWN → HIPS_SAGGING/PIKED → TOO_FAST → TOO_SLOW → IRREGULAR_MOTION → INTEGRITY (first failure is the reason);
(3) new YAML constants: `integrity.deviceMotionMaxRms` 0.15 g on more than `deviceMotionFrameShare` 0.20 of a rep's
frames → INTEGRITY (phone moved during the rep); `framing.bboxVisibilityMin` 0.5 and placement ratios side < 0.5,
front > 0.9; (4) quality = floor(100·q + 0.5). Doc 05 updated.

**D-043 — Server wake rules, made exact** — Accepted — 2026-10-20
Executable spec `tools/reference/pushly_ref/wake.py` (vectors `shared/test-vectors/wake`, SQL port tested by
`supabase/tests/041_*`). Fixed where docs 04/08 were open:
(1) *Snapshot (PS-26)*: walking an alarm's version history forward, a version locks the day at
max(validFrom, its own ring time − 15 min) if it is still current then; first lock wins. Moving, disabling or deleting
an alarm in the last 15 min never changes or cancels that day; a challenge alarm created or moved within 15 min
locks at once (moving it into the past means the day is missed) — no edit can dodge a challenge.
(2) Only reps starting ≥ T0 − 30 s (clock tolerance) and ending ≤ T0 + 30 min count. A session that starts after the
deadline = `missed`. Several sessions per morning are allowed; `succeeded` is final, `failed`/`missed` give way only
to a proven success (e.g. an offline phone uploading yesterday's success ≤ 48 h later).
(3) Mode details: beatTheClock window starts at the later of T0 and the logged ring time; sprint success = the
minimum reached inside the window, which must start before the deadline; sets: the next set must start within
rest + 30 s; escalation snoozes are capped at maxSnoozes; sprint difficulty uses minimumReps, sets uses sets×reps.
(4) Days are settled lazily (`app.settle_wake_days`, on every upload and on `get_wake_summary`; a cron comes with
the leaderboards): no session → `missed`, unfinished → `failed`. Days without a challenge alarm are neutral.
Paused days beyond 14 per calendar month count as missed. The streak is re-folded from all wake attempts on every
change, so late uploads can never leave it inconsistent.

**D-046 — Client anti-cheat v1 (doc 06 §2.2–2.4) and the feature trace** — Accepted — 2026-10-20
Executable spec `tools/reference/pushly_ref/integrity.py`, vectors `shared/test-vectors/integrity` (iOS + Android
`SessionMonitor` in the RepEngine packages). Every session sends: a 10 Hz feature trace (t, elbow, body line,
visibility, motion — JSON, raw deflate, base64; never video), `continuity` (feed gaps > 400 ms above 3 / min, or ≥ 5
frozen frames → 1) and `replay` (spread of world-landmark limb lengths). Server: a trace that doesn't show a real dip
for > 20 % of the counted reps → hard `trace_mismatch` (forged log); missing trace → soft flag; continuity 1 → hold;
replay > 0.6 → soft flag. Second person: an image-mode lite landmarker with 2 poses runs on every 30th frame and
pauses counting ("Only one person in frame"). Not built yet: screen flicker / border heuristics and liveness prompts
(doc 06 §2.4a–b, §2.5) — they need real-device data first.

**D-047 — Signed rep logs with per-install device keys (P4-02 part 1)** — Accepted — 2026-10-20
Each install creates a P-256 key (iOS Secure Enclave via CryptoKit, software key in the keychain where there is none;
Android Keystore) and registers the public key with the RPC `register_device` (idempotent per user + key, ≤ 10 active
devices). Uploads are `{log: "<JSON>", signature, deviceId}` — ECDSA/SHA-256 over the exact UTF-8 bytes of `log`, so
no canonical-JSON rules exist to drift between platforms; raw r‖s (iOS) and DER (Android) are both accepted.
Bad signature or a device of another user → hard flag; bare logs from older apps → soft `unsigned_log`. Signing never
blocks an upload (any failure sends the bare log). Part 2 — App Attest / Play Integrity attestation of that key so it
also proves a genuine app — needs a Google Cloud project for Play Integrity and real-device testing (doc 06 §3).

**D-050 — Friends, feed, leaderboards and the push queue (P6-01, P6-03, P6-05 backend)** — Accepted — 2026-10-21
Friendships: one row per pair (`user_a < user_b`); a block replaces the friendship and is visible only to the blocker
— to the blocked user every action looks like "user not found". Limits: 500 friends, 50 requests / day
(`rate_limits`). Activity feed events are written by triggers on the authoritative tables (succeeded wake, achievement,
level up, new best set), kept 30 days, shown 7 days; kudos once per event. Leaderboards: snapshots of the top 1000
per board / scope refreshed every minute by pg_cron, with a `pos` column (doc 11 used `rank` in the key, which breaks
on ties — equal scores share a rank, streak ties go to the longer best pure streak). The all-time push-up board uses a
new `user_stats_alltime.reps_competitive` (verified, on-time reps only). Hidden users (`leaderboard_visible = false`)
appear as "Anonymous athlete" without an id; low-trust users (< 50) are left out and see a would-be rank (shadow).
Friends boards are computed live. Pushes: `app.enqueue_push` applies category prefs, quiet hours (default 22:00–07:00
local, alarm category exempt) and the 5-per-day cap, and collapses by `collapse_key`; `push-send` (pg_cron every
minute via pg_net + Vault) leases rows, sends APNs (token auth) / FCM HTTP v1, retries with backoff (5 attempts) and
drops dead tokens.

**D-051 — Battle backend: settlement from server-received rep events (P7-01/02/05/07)** — Accepted — 2026-10-21
Results are decided on the server from `battle_events` (each rep's end in server time, ms since `start_at`, pushed in
batches by both clients) — capped per player by the reps of their verified battle rep log (`rep_sessions` linked via
`context.battleId`); an unverified log counts 0, a missing log after the timeout counts the events and is flagged.
Mode rules + tie-breaks: `tools/reference/pushly_ref/battle.py` (labelled cases, vectors `battles/results.json`); turns
use window 5 s + min(latency, 0.5 s) and an out-of-turn rep is ignored. MMR: Glicko-2 per battle (vectors
`battles/glicko2.json`, Glickman's example included); trophies via `app.apply_ranked` (vectors `trophies/*`).
Ranked friend battles count at most 3 per pair per UTC day, beyond that they settle with `counted = false`.
Lifecycle: lobby → both `battle_ready` → countdown (`start_at` = now + 3.5 s) → live → `battle_finish` / both logs /
timeout (mode max + 30 s) → settled; leaving before GO cancels, after GO forfeits. Matchmaking is a SQL job every 2 s
(pg_cron seconds schedule) with the doc 07 §3 window, regions after 20 s, trust buckets and no immediate rematch;
clients poll `matchmaking_status`. Seasons: id = (year − 2000) × 100 + month; monthly rollover soft-resets above
2000 and clears floors. LiveKit tokens come from the `battle-token` function (HS256, 15 min, ranked = camera only).

**D-052 — Clans backend (P8-01, P8-03, P8-05, P8-06)** — Accepted — 2026-10-21
All clan changes are RPCs that check the caller's role (doc 09 §2) and write `clan_events` + system chat messages.
War reps are counted by a trigger on `user_stats_daily` (verified, on-time reps of a UTC day, all contexts), so the
capped day total (`app.clan_war_day_total`, vectors `clan-war/*`) is always recomputed from the day's raw reps —
sessions can arrive in any order. Trust 30–49 counts ×0.5, < 30 counts 0. Roster = members at war start; leaving
keeps earlier reps (`left_at`). Matching: Monday 00:00 UTC, clans with ≥ 5 members and war on, paired within ±20 %
active members by closest rating (else closest size), never last week's opponent, odd one out gets a bye. Finalize:
score → contributors with ≥ 50 counted reps → earlier time the final score was reached; Elo K = 32. Chest tiers and
MVPs are recorded in `clan_wars.result`; granting cosmetic items waits for the items / inventory tables (Phase 10).
The clans board is computed live (`get_clan_leaderboard`, rating or this week's war score). Chat: members-only RLS
(Realtime), 1 msg / 2 s and 200 / day, server-side profanity masking with a small word list (names containing one are
refused), fixed reactions 👊 🔥 💪, @mentions push. Leaders inactive 14 days hand over automatically (daily job).

**D-062 — Rep engine spec v2: image-plane elbow angle, relaxed lockout, real FRONT mode** — Accepted — 2026-10-22
Driven by the founder's first real recordings (`shared/test-vectors/pushup/real-*`): v1 counted **0 of 28** real reps.
Side-on, MediaPipe world landmarks squash the elbow (a straight arm read 120–150°), and real fast reps rarely lock out
fully; from the front the legs are hidden and the shoulder→ankle "tilt" was 50–80°, so the plank never started.
Changes (spec file stays `pushup-v1.yaml`, `specVersion: 2`, codegen `PushupSpecV2`):
1. Elbow angle from **image pixels** (aspect-correct), not world landmarks. FRONT = mean of both arms.
2. **Relaxed lockout**: a rep's top counts at `elbow ≥ topMinDeg (155)` **or** `elbow ≥ lockoutMinDeg (120)` with the
   shoulder back within `depth.lockoutMaxRatio (0.45)` upper arms of the set's last full-lockout height. Plank entry
   still needs 155°. The next descent starts `descentDropDeg (10)` below the angle reached at that top.
   `NOT_DEEP_ENOUGH` = back at a (relaxed) top after dropping ≥ 10° without a bottom.
3. **FRONT mode** (locked at plank entry, released at NOT_READY): visibility = min over both shoulders/elbows/wrists;
   plank = arms straight + wrists ≥ `front.plankWristDropMin (1.0)` upper arms below the shoulders; plank lost when the
   wrists are no longer below the shoulders; no body-line / knee / tilt checks (not measurable); depth from the
   shoulder midpoint; quality body-line part = neutral 0.5; guidance skips the whole-body size check.
4. Server trace check per spec version: top ≥ 145° (v1) / ≥ 115° (v2); `SUPPORTED_SPEC_VERSIONS = {1, 2}`.
5. Synthetic scenarios adjusted to the new definition: `form-no-lockout` oscillates 85↔112°, `form-irregular` wiggles
   below 120°, `form-too-slow` uses 7 s halves.
Result: real side 10/10 and 11 (human said 10, the landmarks show 11 dips — tolerance 1), real front 8/8; all 25
synthetic vectors unchanged in outcome. Trade-off: FRONT is easier to fool (no leg checks) — see Q-11.
